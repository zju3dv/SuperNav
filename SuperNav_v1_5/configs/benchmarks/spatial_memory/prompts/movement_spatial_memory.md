- `hab_navigate_to_memory_node_occ(node_id="area-3")` - two-step occupancy-map navigation toward a memory node, or toward an ephemeral `slam_area_<N>` target from the latest current SLAM area segmentation, using only the current Cartographer SLAM occupancy map. First call previews the occupancy A* route and returns `confirm_token` without moving. Second call repeats the same `node_id` with `confirm_token` to execute bounded primitive turn/forward actions.
  * Use this for remembered memory nodes drawn as black numbered labels on the latest `2d_slam_map`, especially when the target node is outside the current RGB view. You may also use generated white `A<N>` labels from `2d_slam_map.slam_area_nodes` by passing `node_id="slam_area_<N>"` when you need to move to an unmarked geometric area.
  * Preview can succeed only when the latest `2d_slam_map.status` is `current`. If the map is `static`, `pending`, unavailable, or the tool returns `slam_pose_not_current`, make an observation-bearing movement or turn, inspect the fresh SLAM map, then retry.
  * Choose `node_id` from memory-node tools, the `memory_nodes` listed with the latest SLAM map, or the generated `slam_area_nodes` listed with the latest current SLAM map. Do not invent node ids.
  * `slam_area_<N>` targets are temporary geometric exploration/navigation targets, not semantic memory. Their stored pose may be snapped from the area center to a nearby clear cell on the planning occupancy map. After moving to one, inspect the panorama/RGB evidence before creating or updating memory nodes. Treat any area caption only as supporting visual evidence, never as a memory fact or proof of room identity.
  * Treat `status: preview_ready` as a route self-check, not movement and not proof that the route is semantically correct.
  * It uses the node's stored or generated SLAM pose and the raw occupancy map, not GT/navmesh route planning.
  * During confirmed execution, the backend replans from the current position after collision, blocked status, or no-progress/stuck motion. After it returns, inspect fresh `panorama_images` and `2d_slam_map` before choosing another action.
  * Do not assume the navigation result reached the intended node just because the call returned `ok`, `en_route`, or fresh images. Check the returned SLAM occupancy map: compare the yellow/red current pose with the intended memory-node label/route context, and verify the RGB view matches the target node's landmarks. If the pose appears in the wrong room, at the middle of the route, or still far from the target node, treat the memory-node navigation as incomplete/inaccurate instead of claiming arrival. If the RGB view shows the current position close to obstacles or walls, step aside and try again. If you are in an unexpected location, continue with a new node route, visual point navigation, or local observation.
  * If it returns `node_missing_slam_pose`, `slam_pose_not_current`, `unreachable`, `blocked`, or `invalid_confirm_token`, discard the token and use local observation, visual point navigation, or another memory node.

- `hab_visual_point_navigate(view="front", point=[0.5,0.8])` - one-call visual point navigation toward a visible point in a latest panorama image.
  * Use this when the desired local target/proxy is visible in RGB, or when you need a short local adjustment before memory-node routing.
  * Prefer `view` over `image_ref`. Valid views are `front`, `right`, `back`, and `left`, matching the latest `panorama_images`.
  * Choose `view` by which panorama image visibly contains the target/proxy. If the target is visible in the front image, use `view="front"` even when it appears on the right or left side of that front image.
  * Coordinates are normalized image coordinates: x/y `0.0` is left/top, `1.0` is right/bottom.
  * The four panorama images include slim reference lines at normalized x/y coordinates `1/3` and `2/3`; use them only as visual guides for estimating `point=[x,y]`.
  * Use point only. Do not pass bbox in this arm.
  * The call moves immediately when the selected point is reachable. There is no preview/confirmation round trip and no `confirm_token` for this tool in this experiment. Inspect returned `overlay_image`, `selected_anchor`, `panorama_images`, and `2d_slam_map` after it returns.
  * Prefer omitting `max_steps` so the backend can use its normal bounded-hop budget. If you need to pass `max_steps` explicitly, pass a value larger than 40, such as `max_steps=50`. Do not pass small values; turn-only primitive actions can consume the budget and produce near-zero translation.
  * For visible objects, click one precise point on the object's near/lower visible edge or the reachable floor immediately in front of it.
  * For door navigation, click the floor just in front of the door frame, aligned with the vertical centerline through the bottom of the door frame, not the door panel or wall.
  * For floor patches, corridor openings, or other free-form visual targets, click the center of reachable open floor that would produce meaningful movement.
  * Do not click pale, blank, or featureless walls. Select points that correspond to reachable floor, a doorway threshold, an object base, or another visual anchor likely to move the agent usefully.
  * Direction labels are relative to the current capture only. They expire after every movement, turn, or new panorama capture.

Decision rules:
- Use memory-node tools to identify semantic candidate nodes, then use the current SLAM map to choose the next off-screen memory node or generated `slam_area_<N>` geometry target.
- Prefer `hab_navigate_to_memory_node_occ` when the intended waypoint is a known memory node outside the current RGB view, or a listed `slam_area_<N>` target for an unmarked area, and the SLAM map is current.
- Prefer `hab_visual_point_navigate` when the immediate target is visible in RGB, when the SLAM map is not current, or when local geometry needs a small adjustment before a node route.
- After every movement result, first inspect `panorama_images`, `2d_slam_map`, and any memory-node overlay. For memory-node navigation, explicitly check where the agent pose lands on the SLAM map relative to the intended memory-node label; the navigation result may be inaccurate. Do not reuse old `view`, `image_ref`, `point`, or `node_id` route assumptions without checking the fresh state.
- Do not call `hab_navigate_to_memory_node`, `hab_visual_local_navigate`, `hab_visual_overlay_navigate`, `hab_visual_ground_preview`, or `hab_navigate_wam` in this arm.
